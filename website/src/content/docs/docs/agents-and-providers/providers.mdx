Frogg does not ship a model or an agent of its own. The daemon runs agent CLIs that you
install and sign in to on the daemon host. Each one is a **provider**.

<Screenshot src={appHostProvidersImg} alt="Host settings, Providers" />

## Built-in providers

| ID         | Name      | Runs                                   | Default mode | Enabled |
| ---------- | --------- | -------------------------------------- | ------------ | ------- |
| `claude`   | Claude    | `claude` (Claude Code, via the Agent SDK) | `auto`    | yes |
| `codex`    | Codex     | `codex app-server`                     | `auto-review` | yes |
| `copilot`  | Copilot   | `copilot --acp`                        | agent        | yes |
| `opencode` | OpenCode  | `opencode` server with a bridge plugin | set by OpenCode | yes |
| `pi`       | Pi        | `pi --mode rpc` (`PI_COMMAND` overrides) | none       | yes |
| `omp`      | Oh My Pi  | `omp` (`OMP_COMMAND` overrides)        | `full`       | **no** |

Any agent that speaks the [Agent Client Protocol](https://agentclientprotocol.com) can be
added as a custom provider; see [custom providers](/docs/agents-and-providers/custom-providers/).

## Install and sign in

Install the CLI and log in **as the user the daemon runs as**. Frogg uses each CLI's own
authentication and never asks for your provider credentials.

```sh
# examples; follow each vendor's instructions
npm install -g @anthropic-ai/claude-code && claude
npm install -g @openai/codex && codex login
```

The daemon finds binaries on its `PATH`. A service installed by `install.sh` inherits the
`PATH` of the shell that ran the installer. If you install a CLI later into a directory
that was not on that `PATH`, re-run the installer or point the provider at the binary with
a `command` override.

After installing, refresh:

```sh
frogg restart
frogg provider ls
```

```text
PROVIDER  LABEL     STATUS     ENABLED   DEFAULT MODE
claude    Claude    available  Enabled   auto
codex     Codex     available  Enabled   auto-review
copilot   Copilot   not found  Enabled   ...
opencode  OpenCode  not found  Enabled   default
pi        Pi        not found  Enabled   default
omp       Oh My Pi  not found  Disabled  full
```

## Diagnose

```sh
frogg provider diagnostic claude
```

It shows how the command resolved, the binary version, auth status (for Claude, the
output of `claude auth status`) and relevant environment. In the app, expand a provider in
**host settings → Providers**.

## Models, modes and thinking

Models are discovered from each provider at runtime:

```sh
frogg provider models claude
frogg provider models codex --thinking
```

Pick them per agent in the composer, or on the CLI with `--provider codex/gpt-5.5`,
`--model`, `--mode` and `--thinking`. Modes are covered in
[permissions](/docs/using-frogg/permissions/).

Some providers expose toggles in the composer: **Fast mode** (Claude, Codex), **Plan mode**
(Codex) and **Auto accept** (OpenCode and ACP agents).

## Enable, disable, reorder

Toggle providers in **host settings → Providers**, or in config:

```json title="~/.frogg/config.json"
{
  "agents": {
    "providers": {
      "omp": { "enabled": true },
      "copilot": { "enabled": false },
      "claude": { "command": ["/opt/claude/bin/claude"], "order": 1 }
    }
  }
}
```

Apply with `frogg reload`.

## Provider accounts (multi-sign-in)

A provider CLI keeps its sign-in in one config directory. Frogg can manage more than one of
those directories so you can switch between logins — a personal and a work Claude
subscription, for example — without signing out.

Creating an account makes `<home>/.claude-<name>` and symlinks the shared folders
(`commands`, `skills`, `agents`, `projects`, `sessions`, `shell-snapshots`) back to the
primary `~/.claude`, so commands, skills and history stay shared while credentials do not.
You pick which folders to link; a folder that does not exist in the primary directory is
skipped with a warning. On Windows, creating symlinks needs Developer Mode or an elevated
shell; links that fail are reported per folder and the account still works.

Account names are lowercase slugs (`[a-z0-9-]`, no leading, trailing or doubled hyphens).

Sign an account in by opening a terminal for it: the daemon launches the provider's
interactive login command with `CLAUDE_CONFIG_DIR` pointed at that account's directory, and
you run `/login` inside it. An account shows as authenticated once its credential file
(`.credentials.json`) exists.

Deleting an account only removes it from Frogg's list — the config directory, and the
credentials in it, are left on disk for you to remove. An agent that was launched with an
account you later delete keeps working: its next launch quietly falls back to the provider's
default account and the daemon logs a warning.

### Which account an agent uses

The account is picked **per agent, when the agent is created**, and it sticks: the agent keeps
that account when it is resumed or rehydrated after a daemon restart. Changing an agent's
account means starting a new agent.

An agent can be launched with:

- **Default** — the provider's primary config directory (`~/.claude`), ignoring whichever
  account is marked active,
- any account configured for that provider,
- or no choice at all, which uses the provider's **active** account — the same daemon-wide
  behaviour as before, and what every existing agent keeps doing.

Resolution order for the provider's config-directory variable (`CLAUDE_CONFIG_DIR` for
Claude), highest first:

1. an explicit `agents.providers.<id>.env` in
   [`config.json`](/docs/reference/configuration/#agents),
2. the account chosen for that agent,
3. the provider's daemon-wide active account.

**Make active** therefore sets the default for agents that do not choose, and no longer
silently retargets every agent on the provider.

#### Picking it in the composer

The composer shows an **account** control immediately to the right of the model selector. It
appears only when the provider actually has accounts — a provider with none, or one whose
accounts capability is off, shows the same row of controls as before.

The list is **Default** followed by every account for that provider. **Default** always means
the primary config directory, so it is never relabelled with the active account's name — that
account has its own row. An account that is not signed in yet is shown greyed out with
*Not signed in* and cannot be chosen, rather than launching an agent that would fail to
authenticate.

The choice applies to the agent you are about to start. Adding, removing or signing in to an
account updates an open composer straight away — there is nothing to refresh.

Once the agent is running, the account control stays in the chat composer but is greyed out
and does not open: it names the account the agent runs as, including the active account it
resolved to when the agent was launched without a choice. Because the account is fixed at
launch, start a new agent to use a different one.

#### Seeing it in the sidebar

A workspace row shows a small account glyph beside its title when its agent runs under a
provider that has accounts. It is icon only, so the row's trailing slot keeps showing the diff
stat or timestamp; hover the glyph to read the account name. A workspace with several agents
reports the newest one, which is the agent the row's title and status already describe.

### From the app

**Host settings → Providers → Provider sign-ins** lists every provider whose accounts the
daemon has enabled, with that provider's accounts under it. Each row shows the account name,
its config directory, whether it is signed in, and whether it is the active account, with
actions to make it active, sign it in, and remove it. The section is hidden entirely on a
daemon that does not report the feature.

<Steps>

1. **Add account** opens a form. Type a name: the page validates it as you type and shows the
   slug and the config directory that will be created. Every shareable folder is checked by
   default; uncheck the ones this account should keep to itself.
2. **Sign in** opens a Frogg terminal running that provider's own login with the account's
   config directory applied — for Claude, run `/login` in it. Terminals belong to a workspace,
   so the action needs at least one workspace on the host; it is disabled when there is none.
3. **Refresh** re-reads the list once the CLI's login finishes, which is what flips the row to
   signed in.
4. **Make active** makes that account the default for agents that do not pick one in the
   composer. **Remove** asks first and then tells you the config directory it left behind.

</Steps>

Provisioning warnings from the daemon — a folder it could not link, for example — are shown
verbatim next to the list, and a rejected name or duplicate keeps the form open with what you
typed.

Only Claude has accounts enabled. Other providers are declared but off; turn one on with
`providerAccounts.<provider>.enabled` in
[`config.json`](/docs/reference/configuration/#provideraccounts) once its layout is
verified.

## Usage and limits

**Host settings → Usage** shows provider-reported quota where the provider exposes it
(for example Claude, Codex and Kimi). Frogg reads those credentials read-only; the CLIs own
token refresh.

## Provider environment

Agents inherit the daemon's environment plus anything you set per provider (`env` in
config) or per run (`frogg agent run --env KEY=value`). Common variables:
`ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`,
`OPENAI_API_KEY`, `OPENAI_BASE_URL`.

## Claude

Multiple Claude sign-ins are managed by
[provider accounts](#provider-accounts-multi-sign-in): **Host settings → Providers →
Provider sign-ins**. Each account gets its own `CLAUDE_CONFIG_DIR` under
`<home>/.claude-<name>`, keeping credentials, settings and history private while the folders
you chose stay symlinked to the primary `~/.claude`.

Frogg never signs an account in for you. **Sign in** opens a terminal with that account's
config directory applied, equivalent to:

```sh
CLAUDE_CONFIG_DIR="$HOME/.claude-<name>" claude
```

then run `/login` inside it.

:::caution[Removed in this fork]
Earlier releases let you declare an extra Claude account as a custom provider with a
`params.claudeAccount` profile in `config.json`. That mechanism has been removed in favour of
provider accounts. Such entries are now ignored — the daemon logs a warning naming them at
startup, and the providers they declare launch against the default Claude config directory.
Recreate the accounts under **Provider sign-ins** and delete the stale
`agents.providers.<id>` entries from `config.json`.
:::
