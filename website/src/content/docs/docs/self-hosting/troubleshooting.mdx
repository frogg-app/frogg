## Start with facts

Work out **which daemon** has the problem and **how the client reaches it** before changing
anything. A local `frogg status` describes the daemon for that CLI's `FROGG_HOME`, which may
not be the host you are looking at in the app.

```sh
frogg status                     # home, listen, PID, log path, versions, providers
frogg auth claim-status          # pairing, password and LAN trust
frogg provider diagnostic claude # binary, version, auth for one provider
frogg update --check             # what version is available
tail -n 100 ~/.frogg/daemon.log
```

In the app, **Settings → About** shows the app version; **host settings → Overview**
shows the daemon's version and update state; **Settings → Diagnostics** collects a report.

## Daemon

| Symptom | Cause and fix |
| ------- | ------------- |
| `Another Frogg daemon is already running (PID n)` | A daemon already uses this `FROGG_HOME`. `frogg stop`, or use another home |
| `Daemon failed to start in background` | Read the log lines printed after it. Common: port in use, invalid config |
| `[Config] Invalid config in ~/.frogg/config.json` | A key is misspelt or has the wrong type. The message names the path. See [configuration](/docs/reference/configuration/) |
| Log: `Relay is enabled but no relay endpoint is configured` | Relay is on with no endpoint, so the daemon runs without relay and pairing offers are direct only. Set the endpoint in host settings, **Pair devices**, or `daemon.relay.endpoint`, or turn relay off |
| Log: `Worker crashed (code 1): Frogg cannot listen on 0.0.0.0:9999: port 9999 is already in use by a fde daemon 0.6.13 (server …), pid N (node). Restarting worker in 4s (attempt 3)` | Something else holds the port; the line names it (daemon identity, pid and process name where it can find them). The worker keeps retrying with backoff up to 30 s. Stop the holder. For a leftover FDE service, see [legacy FDE service](#legacy-fde-service-holds-the-port) |
| `frogg status` shows `Managed By: detached` | A daemon is running outside the service that is meant to own it, so the next `systemctl start` (an upgrade, a reboot) hits `EADDRINUSE`. `frogg restart` hands it back. See [the service and the daemon disagree](#the-service-and-the-daemon-disagree) |
| `frogg status` shows `Managed By: service_stopped` | The unit is installed but not running and nothing holds the port. `frogg start` starts the unit |
| Service stops when you log out (Linux) | `sudo loginctl enable-linger $USER` |
| Changes to `config.json` ignored | `frogg reload`; check its output for paths that need `frogg restart` or are pinned by env vars |

### The service and the daemon disagree

`frogg status` reports both the registered service and who is actually running the daemon:

```
Service      systemd frogg-daemon.service (enabled, inactive)
Managed By   detached
```

`detached` means a daemon holds the port while its unit sits inactive: the unit cannot start
while the port is taken, so the next upgrade or reboot fails. It happens when a daemon was
started by hand, or when a restart was interrupted. `frogg restart` stops the stray daemon and
restarts the service; `frogg start` starts an inactive unit rather than another loose daemon.

A restart issued from a terminal the daemon hosts is a special case: stopping the unit kills
every process in its cgroup, including that terminal and the command issuing the stop. Frogg
hands those restarts to a transient `systemd-run --user` unit that outlives the stop, so the
daemon does come back — but the terminal it was typed in ends with the daemon. Reconnect and
run `frogg status` to confirm.

## Connections

| Symptom | Cause and fix |
| ------- | ------------- |
| `Cannot reach the daemon at <host>` (CLI) | Not running, wrong port, or firewall. `frogg status` on the host; pass `--host` or set `FROGG_HOST` |
| `Daemon is reachable ... but requires a password` | Set `FROGG_PASSWORD` for the CLI, or enter it in the app |
| `This app requires daemon 0.6.0 or later` | Update the daemon, then restart its service. If you already updated, the old process is still running |
| `403 Invalid Host header` | You used a hostname the daemon does not allow. Add it to `daemon.hostnames` or `FROGG_HOSTNAMES` |
| Browser shows a pairing page | Your address is not loopback or private (for example Tailscale's `100.x`). Pair the device or set a password |
| TLS error in Direct connection | Turn off **Use SSL** unless a TLS proxy fronts the daemon |
| LAN scan finds nothing | Scans cover your local subnets only. Enter the address manually; check the daemon listens on `0.0.0.0` |
| Pairing link fails on a phone | The phone cannot reach any address in the offer. Join the same network or VPN, or set `FROGG_PRIMARY_LAN_IP` |
| Host shows "A different daemon (…) is answering at this host's address, not this host (…)" | The saved host's address now answers with another daemon: a different install, or another product such as a leftover FDE service. The app refuses it, so it never shows another daemon's agents as this host, and keeps retrying. Stop the other daemon or fix the address; the host reconnects on its own. The same condition is logged as `daemon_client_server_identity_mismatch` |
| Remote SSH `refused your SSH keys` | Enter the SSH password, or fix key auth so `ssh host` works in a terminal |

## Providers and agents

| Symptom | Cause and fix |
| ------- | ------------- |
| Provider `not found` | The CLI is not on the daemon's `PATH`. Install it for the daemon's user, re-run the installer or `frogg install-service`, `frogg restart`. Or set `command` in `agents.providers` |
| Provider found but agents fail to start | Not signed in as the daemon's user. `frogg provider diagnostic <id>` shows auth status |
| Model list empty or stale | Catalog refresh timed out. Raise `agents.catalogRefreshTimeoutMs`, then reload |
| Agent waits forever | It is waiting for a permission. `frogg permissions ls` |
| New skills or MCP servers not seen | `frogg agent reload <id>` restarts the provider process |
| `Caller agent ... not found` from the CLI | The shell runs inside an agent (`FROGG_AGENT_ID` is set) and the target daemon does not know that agent. Unset `FROGG_AGENT_ID` |

## Voice and Companion

| Symptom | Cause and fix |
| ------- | ------------- |
| Dictation or voice alerts unavailable | Voice is off on the daemon: the local speech runtime is unavailable, or `features.voice.enabled` is `false`. Check the daemon log |
| First use is slow | Local speech models are downloading to `~/.frogg/models/local-speech` |
| `Sign in to Claude Code or Codex on this daemon.` | Companion needs a signed-in subscription CLI, or `features.companion.backend: "api"` with an Anthropic key |
| `Another device is using Companion on this daemon.` | One conversation per daemon. End it on the other device |

## Updates

| Symptom | Cause and fix |
| ------- | ------------- |
| `release check failed: HTTP 403` | GitHub rate limit. Set `FROGG_GITHUB_TOKEN` or sign in with `gh auth login` |
| `cannot self-update: ...` | Not an `install.sh` install (Docker, Nix, dev checkout). See [updates](/docs/self-hosting/updates/#not-self-updatable) |
| `update to X failed and was rolled back to Y` | The new version did not become healthy. Read `~/.local/share/frogg/self-update.log` and the daemon log |
| `update to X blocked: ... foreign ...`, or `restored X without verifying it (the port is held by another daemon)` | Another daemon holds the listen port, so the new version could not be verified. The updater retires a legacy `fde-daemon` service on the same port by itself; anything else you stop by hand, then run `frogg update` again. See below |
| Automatic update keeps not applying | Each failed attempt at a version waits longer before the next, up to seven days. Fix the cause, then use **Update now** or `frogg update` |
| Desktop: no update found | You may be on Stable while the release is a beta, or the release lacks updater files |

### Legacy FDE service holds the port

Frogg was called FDE before 1.0. An `fde-daemon` service left enabled from then can start on
the same port and win the race after a restart, so updates fail and the app reports a
different daemon. The self-updater disables it when it sees this; to do it yourself:

```sh
systemctl --user disable --now fde-daemon.service   # macOS: launchctl bootout gui/$(id -u)/app.frogg.fde-daemon
systemctl --user restart frogg-daemon.service
```

The unit file is left in place; remove it once you no longer need it. Carry any
`Environment=FDE_...` lines over as `FROGG_...` first, as described in
[moving from FDE](/docs/self-hosting/updates/#moving-from-fde).

## Getting help

Open an issue at [github.com/frogg-app/frogg/issues](https://github.com/frogg-app/frogg/issues)
with `frogg status --json` output (review it before posting), the relevant log lines, your
client version and how you connect.
