Install with the script, Docker or Nix first; see [install](/docs/getting-started/install/).
This page covers operating a daemon once it is there.

## Service or foreground

`install.sh` registers a login service. Manage it with the CLI or the service manager:

| Platform | Service | Logs |
| -------- | ------- | ---- |
| Linux    | systemd user unit `frogg-daemon.service` | `journalctl --user -u frogg-daemon -f`, and `~/.frogg/daemon.log` |
| macOS    | launchd agent `app.frogg.frogg-daemon` | `~/Library/Logs/app.frogg.frogg-daemon.log`, and `~/.frogg/daemon.log` |
| Windows  | Scheduled task created by `frogg install-service` | `%USERPROFILE%\.frogg\daemon.log` |

```sh
frogg status
frogg restart
frogg stop
frogg install-service --listen 0.0.0.0:9999   # (re)create the login service
frogg uninstall-service
```

Without a service, run it yourself:

```sh
frogg start                      # background; prints PID and log path
frogg start --foreground         # stay attached, for containers and supervisors
```

Only one daemon can use a home directory. A second start fails with
`Another Frogg daemon is already running (PID ...)`.

## Listen address

Stock Frogg defaults to `0.0.0.0:9999`: every interface, port 9999. A brand can ship a
loopback bind instead (`127.0.0.1:9999`), and then nothing off this machine connects until
you set an address yourself. `config.json` has no `daemon.listen` until you write one, so
the brand default applies to a fresh install and your own value always wins.

```sh
frogg restart --listen 127.0.0.1:9999        # this machine only (use with SSH or a proxy)
frogg restart --port 9443
frogg restart --listen /run/user/1000/frogg.sock
```

Persist it in `config.json` as `daemon.listen`, or with `FROGG_LISTEN`. The CLI on the same
machine finds the daemon through its socket or pipe automatically.

## State

Everything lives in `FROGG_HOME` (`~/.frogg`): `config.json`, agents, projects, schedules,
worktrees, paired devices, logs and speech models. Back it up to keep history and
pairings. See [configuration](/docs/reference/configuration/#other-files-in-frogg_home).

## Scratch files and cleanup

The daemon keeps its scratch work in the system temp directory (`os.tmpdir()`), never in
your home folder. Each entry is named `frogg-<kind>-<pid>-…` (image attachments, Pi MCP and
extension files, speech uploads), so its owner is identifiable. The only scratch space
outside temp is a `.frogg-clone-*` directory next to a GitHub clone's target, which the
clone renames into place and removes on failure.

On start, the daemon removes debris earlier processes left behind, in the background:

- temp entries whose owning process has exited (after a 10-minute grace period), and
  older unnumbered `frogg-<kind>-XXXXXX` entries after 24 hours;
- `.frogg-clone-*` directories older than 24 hours beside registered projects;
- empty `~/frogg-classify-home-*` directories left by old test runs.

It matches exact names only, skips symlinks, entries owned by another user and anything a
live process holds, and logs what it removed. A sweep failure never stops the daemon.

### Resources in the app

Host settings → **Host** has a **Resources** section when the daemon supports it
(`features.hostResources`; older daemons hide it):

- **Live load.** Host CPU (with core count and load average where the OS reports one),
  memory, and the disk holding `FROGG_HOME`, as usage bars that refresh every 5 seconds
  while settings is open. The daemon process row shows its PID, RSS and heap, CPU as a
  share of one core (it can exceed 100%), and uptime.
- **Owned storage.** The size and entry count of each area Frogg owns: logs, agent state,
  projects, Frogg worktrees, agent worktrees, provider accounts, uploads, project import
  staging, speech cache, models, daemon versions and temp. Sizes are cached on the daemon for
  5 minutes; **Refresh** remeasures. A size prefixed with `≥` is a lower bound, because the
  walk stopped at its entry cap.
  - **Agent worktrees** are the linked Git worktrees of every registered project that Frogg
    did not create, such as Claude Code's `.claude/worktrees/agent-*` and Codex's
    `~/.codex/worktrees`. Repositories behind worktrees in provider account directories are
    found even when they are not registered projects.
  - **Provider accounts** is the combined size of each provider's default config directory
    (`~/.claude`, `~/.codex`, …) and every added account's directory.
- **Clean.** Owners can clean five areas after a confirmation: rotated logs (never the live
  `daemon.log`), the spoken alert cache (`tts-cache`), stale temp debris, and stale Frogg and
  agent worktrees. The result shows what was freed, then the list remeasures. Other areas are
  shown for size only.

### Stale worktrees

A worktree is stale when it is not locked, has no uncommitted or untracked changes, no active
workspace, project or agent runs inside it, and either its `HEAD` is merged into the default
branch and it has been idle a day, or it has been idle longer than the retention period
(7 days). A detached `HEAD` that is not merged is never stale. Removing a worktree keeps its
branch, so committed work survives; ignored files such as `node_modules` go with it.

The daemon removes stale worktrees 5 minutes after start and every 6 hours. Set
`daemon.worktreeRetentionDays` in `config.json` to change the retention period, or `0` to
turn off the automatic sweep and the idle rule (merged worktrees can still be cleaned by hand).
The setting is read at startup.

Viewers see metrics only; storage sizes need the operator role and cleaning needs owner. See
[device roles](/docs/getting-started/connect-and-pair/#device-roles).

## Logs

```sh
frogg status | grep Logs
tail -f ~/.frogg/daemon.log
```

The log is JSON by default and rotates at 10 MB, keeping three files. Readable output:

```sh
FROGG_LOG_FORMAT=pretty FROGG_LOG_LEVEL=debug frogg start --foreground
```

Authorization headers are redacted. When a background start fails, the CLI prints the
last log lines.

## Agent CLIs and PATH

Agents inherit the daemon's environment. A service keeps the `PATH` it was installed
with. After installing a new agent CLI into a new location, re-run the installer or
`frogg install-service`, then `frogg restart`. Put provider API keys in the service's
environment rather than your shell profile.

## Keep agents alive across restarts

By default, restarting the daemon stops agent processes; agents that were mid-turn are
resumed with a continuation prompt when the daemon comes back (within an hour).

Opt-in **independent execution** keeps agent runtimes in a separate process so they survive
daemon restarts and updates:

```sh
FROGG_EXECUTION_SERVICE=1 frogg restart
frogg execution-status
frogg stop --all      # stop the daemon and the execution service with its agents
```

Set `FROGG_EXECUTION_SERVICE=1` in the service environment to make it permanent.

## Several daemons on one machine

Give each its own home and ports (the web client port too, if it serves one); keep clear of
the ports frogg and frogg beta use (9999/9998 and 9989/9988):

```sh
FROGG_HOME=~/.frogg-work FROGG_WEB_UI_PORT=9978 frogg start --listen 0.0.0.0:9979
FROGG_HOME=~/.frogg-work frogg status
```

Use `--host` or `FROGG_HOST` to point CLI commands at the right one.

## Reload configuration

```sh
frogg reload
```

It reports settings applied live, settings that need `frogg restart`, and settings pinned by
env vars or flags.
