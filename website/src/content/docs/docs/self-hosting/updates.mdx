Clients and daemons update separately. Keep them close: from 0.6, apps require daemon
0.6.0 or later, and `CHANGELOG.md` marks releases that need both updated together.

## Daemons installed with `install.sh`

```sh
frogg update --check
frogg update
frogg update --channel beta
frogg update --to 0.6.18        # pin a version, including older ones
```

How it works:

1. Finds the release on GitHub (`frogg-app/frogg`) for the channel. **Stable** ignores
   prereleases (`-beta.N`); **beta** includes them.
2. Downloads the daemon bundle, verifies its `.sha256`, and unpacks it to
   `~/.local/share/frogg/versions/<version>`.
3. Switches the `current` link, restarts the service (from a transient `systemd-run` unit
   when the updater itself runs inside the daemon's cgroup, so the stop cannot kill the
   restart), and waits up to 90 seconds for
   `/api/identity` to report the new version and `/api/health` to answer.
4. If that fails, switches back to the previous version, restarts, and exits with code 2.

If the address answers with a different daemon (another product, such as a leftover FDE
service, or another install), the updater stops and disables a legacy `fde-daemon` service
that uses the same port, logs `stopping and disabling legacy service fde-daemon.service`, and
restarts once more. If the port is still held by another daemon, it does not roll back the
bundle for a fault it did not cause: it restores the version that was running, without the
90-second check, and records `failed` with `restored X without verifying it (the port is held
by another daemon)`. See [troubleshooting](/docs/self-hosting/troubleshooting/#updates).

The result is recorded in `~/.local/share/frogg/last-update.json`; details in
`self-update.log` next to it. The three newest versions are kept.

The same update runs from the app: **host settings → Overview → Daemon updates**.

### Automatic updates

```json title="~/.frogg/config.json"
{
  "daemon": {
    "autoUpdate": { "enabled": true, "channel": "stable", "checkIntervalHours": 24, "quietHours": [9, 18] }
  }
}
```

The first check runs five minutes after start. Every check logs its result and the time of
the next one, whether or not it found anything:

```
auto-update checked  outcome=up_to_date  nextCheckAt=2026-09-20T12:00:00.000Z
```

Check `~/.frogg/daemon.log` for that line before concluding that automatic updates have
stopped: with the default `checkIntervalHours` of 24, a release published just after a check
waits until the next one. Lower the interval if you track releases closely.

An update waits while agents are running
or during quiet hours (local time; `[9, 18]` means 09:00 to 18:00), retrying every 15
minutes.

A version whose automatic update did not apply is not retried on every check, because each
attempt restarts the daemon and disconnects clients. The next attempt at that version waits
one check interval, then twice as long after each further failure, up to seven days. The
count is kept in `~/.frogg/daemon-update/auto-update-attempts.json`, so it survives the
restarts. It resets when a newer release appears or the daemon is up to date. **Update now**
in the app and `frogg update` are never held back.

### Rate limits and mirrors

GitHub's API allows 60 unauthenticated requests an hour. On a 403 or 429 the updater tries
`GH_TOKEN`, `GITHUB_TOKEN` or `gh auth token`; set `FROGG_GITHUB_TOKEN` to always use a token.
Point at a mirror with `FROGG_RELEASE_BASE` (`<base>/download/v<version>/<asset>`) and
`FROGG_RELEASES_API`.

### Rolling back to 1.5.28 or earlier

1.5.29 changed the paired-device file, `~/.frogg/principals.json`, from version 1 to
version 2. Older daemons can't read version 2, so a plain `frogg update --to 1.5.28`
leaves the daemon with no paired devices it recognises. Before its first version 2 write,
the daemon copies the original file to `~/.frogg/principals.v1.bak.json` (mode 0600). That
copy is never overwritten.

To roll back:

```sh
frogg daemon stop
cp ~/.frogg/principals.v1.bak.json ~/.frogg/principals.json
chmod 600 ~/.frogg/principals.json
frogg update --to 1.5.28
```

Devices paired after the upgrade aren't in the backup, so pair them again. Role changes and
renames made since the upgrade are lost too. With no backup, the daemon either never had a
version 1 file or was set up on 1.5.29 or later. In that case, remove `principals.json` and
claim the daemon again after rolling back.

## Not self-updatable

`frogg update` refuses and says why for:

| Install | Update by |
| ------- | --------- |
| Docker  | `install-docker.sh --update` with the new image; see [Docker](/docs/self-hosting/docker/#update) |
| Nix     | Bump the flake input and rebuild |
| Dev checkout or manual copy | `git pull` and rebuild, or re-run `install.sh` to switch to a versioned install |
| Custom brand with updates disabled | Your distribution's own process |

## Moving from FDE

Frogg was called FDE before 1.0. The first time the daemon starts, it moves `~/.fde` to
`~/.frogg`. It rewrites the stored workspace and agent paths, repairs the git worktrees it
moved, and moves their Claude Code sessions so agents can resume. The move is skipped while an
FDE daemon is still running, when `FROGG_HOME` is set, or when `~/.frogg` already has data.
The startup output says why.

`FDE_*` environment variables are no longer read. The daemon lists any it finds in its
environment or in an old `fde-daemon` service, with the `FROGG_*` name to use instead.

To move an `install.sh` install:

```sh
fde daemon stop
systemctl --user disable --now fde-daemon   # macOS: launchctl bootout gui/$(id -u)/app.frogg.fde-daemon
curl -fsSL https://frogg.app/install.sh | sh
```

Carry over any `Environment=FDE_...` lines as `FROGG_...`, then remove `~/.local/share/fde`.
Desktop and mobile apps don't update in place across the rename; install them again.

## Desktop and mobile apps

- **Desktop** checks GitHub releases and installs on quit; choose Stable or Beta. See
  [desktop app](/docs/desktop-mobile-cli/desktop/#updates).
- **Android** checks GitHub releases in the app and installs the new APK itself; choose
  Stable or Beta. See [Android and iOS](/docs/desktop-mobile-cli/mobile/#updates).
- The **web app** is served by the daemon, so it updates with the daemon.
