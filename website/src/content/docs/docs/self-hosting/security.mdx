A Frogg daemon can run commands on its host through agents and terminals. Treat access to
it like SSH access to that machine.

## Access policy

| Client connects from | No password | Password set |
| -------------------- | ----------- | ------------ |
| Loopback | Allowed | Password or device credential |
| Private network (RFC 1918, link-local, `fc00::/7`) | Allowed while `trustLan` is on (default for `frogg`) | Password or device credential |
| Anywhere else, including CGNAT `100.64.0.0/10` (Tailscale) | Paired-device credential | Password or device credential |

Two settings override the table:

- `daemon.auth.claimMode` (`FROGG_CLAIM_MODE`). While it is on, the LAN is **not** trusted
  whatever `trustLan` says, and every client needs a credential. See
  [claim mode](#claim-mode).
- A relay connection always needs a device credential. Reaching the daemon through a relay
  is not evidence of anything, so locality never applies to it.

Unauthenticated routes: `/api/identity` (version and brand, used by LAN scans),
`/api/health`, and the device-access routes that are how a device gets its first
credential (`/api/identity/proof`, `/api/setup/claim`, `/api/setup/request`,
`/api/setup/offer`, `/api/auth/login`). All of them are rate-limited per client address.
The web app's static files load without credentials; its API calls do not.

`/api/setup/offer` mints a credential, so it needs one: locality alone never buys a
pairing offer.

Repeated bad credentials from one address are throttled — 10 failures in 5 minutes blocks
that address for 5 minutes, and the daemon answers `429`.

## Claim mode

Claim mode is the locked-down posture for a daemon on a network you do not control.

```json title="~/.frogg/config.json"
{ "daemon": { "auth": { "claimMode": true } } }
```

- LAN clients are untrusted, so `trustLan` is ignored while it is on. `auth.settings.get`
  reports both the configured `trustLan` and the effective `lanTrustEffective`.
- While the daemon is **unclaimed**, the first client to reach `/api/setup/claim` becomes
  the owner. After that, further devices need a pairing code, an owner approval or the
  password. A daemon with a password set already counts as claimed.
- `daemon.auth.claimScope: "local"` (`FROGG_CLAIM_SCOPE=local`) narrows who can claim:
  only a loopback client (after trusted-proxy resolution) presenting the daemon's local
  token (`~/.frogg/local-token`) as its bearer. Everyone else gets `403`. Offers, pairing
  codes and approvals are unaffected. The default is `"any"`. To claim on the host:

  ```sh
  curl -X POST http://127.0.0.1:9999/api/setup/claim \
    -H "Authorization: Bearer $(cat ~/.frogg/local-token)" \
    -H 'content-type: application/json' -d '{"claim":true,"deviceName":"Host"}'
  ```
- The claim is **latched**: revoking every device does not reopen it. Only
  `frogg auth reset-claim` on the daemon host clears it.
- The last owner device cannot be revoked (including signing itself out) or demoted.
  Promote another device to owner first.
- An unclaimed daemon in claim mode that listens beyond loopback logs a warning at
  startup: the first client to reach it becomes its owner.
- Authentication is two-way. The daemon publishes a fingerprint of its long-term key
  (`sha256:` + unpadded base64url of SHA-256 over the raw 32-byte public key); the client
  carries it in the pairing link and checks it against `POST /api/identity/proof`, which
  signs a client-chosen nonce. A daemon that cannot produce the signature is not the daemon
  you meant to pair with.
- Turning claim mode on, or turning `trustLan` off, disconnects the sessions that were
  already relying on LAN trust. It does not wait for their next reconnect.

The stock `frogg` brand ships with claim mode **off**, LAN trust **on** and binds `0.0.0.0`.
A brand can change these defaults, plus `claimScope`, in `brand.json` (see
[the brand manifest](/docs/fork-and-rebrand/brand-manifest/)); any other brand defaults to a loopback bind,
LAN trust off and claim mode on. All are defaults for a daemon you have not configured: a
`daemon.listen` or `daemon.auth.*` value you write in `config.json` wins, as does
`FROGG_LISTEN`, `FROGG_CLAIM_MODE`, `FROGG_TRUST_LAN` or `FROGG_CLAIM_SCOPE` in the daemon's
environment (under a brand's own prefix for a branded build).

### Turning claim mode on and off

```sh
frogg auth claim-mode          # report the mode that applies, and where it came from
frogg auth claim-mode on       # lock the LAN out; the first client claims this daemon
frogg auth claim-mode off      # back to the trusted-LAN, pairing and password rules
```

It writes `daemon.auth.claimMode` and asks a running daemon to reload, so it applies without
a restart. Run it in a shell on the daemon's own machine: loopback is trusted whatever claim
mode says, so this is the way back in if claim mode leaves you locked out of your own daemon.
The legacy spelling `frogg daemon claim-mode` works too.

### Recommended settings

| Deployment | Settings |
| ---------- | -------- |
| Laptop, daemon on the same machine | Defaults, or `--listen 127.0.0.1:9999` if nothing else should connect |
| Home or office LAN you control | Defaults |
| Shared or untrusted LAN | Turn on claim mode (or `frogg auth trust-lan off`) and pair devices with `frogg pair` |
| Tailscale / VPN | Pair devices (CGNAT addresses are not "private"), or set a password |
| Docker | Set `FROGG_PASSWORD`; container networking hides real client addresses |
| Public internet | Do not expose the daemon directly. Use a VPN, SSH, or a TLS reverse proxy plus a password |

## Pairing

Paired devices hold a random credential; the daemon stores only its SHA-256 in
`~/.frogg/principals.json` (mode 0600). See
[connect and pair](/docs/getting-started/connect-and-pair/).

There are four ways a device gets a credential:

| Route | How |
| ----- | --- |
| Pairing code | `frogg pair` mints an 8-symbol code the device types or scans. Single-use, 30–3600 seconds (default 600) |
| Pairing offer | The older single-use offer token behind `frogg auth pair`, valid 10 minutes |
| Owner approval | The device posts to `/api/setup/request` and polls; an owner approves it over `auth.pairing_request.decide` and picks its role |
| Password | `POST /api/auth/login` exchanges the daemon password for a device credential |
| Claim | In claim mode, the first client on an unclaimed daemon claims it as owner |

Pairing codes are Crockford base32 without `I`, `L`, `O` or `U`, displayed as `XXXX-XXXX`,
and the daemon folds the ambiguous characters back (`I`/`L` → `1`, `O` → `0`) so a
mistyped code still works.

### Device roles

Every credential carries one of three roles, enforced by the daemon at admission and on
every request, including streamed input (terminal keystrokes, agent messages, dictation,
file writes):

| Role | Can |
| ---- | --- |
| `owner` | Everything: daemon settings and updates, provider accounts, pairing codes, approving and revoking devices, setting roles, password and claim settings |
| `operator` | Drive work: agent chats, terminals, workspace scripts, file edits, git and forge actions. No daemon settings, no device management |
| `viewer` | Read-only: sessions, timelines, terminal output, file browsing and diffs. No input, no command execution, no writes |

A role never widens what a device was granted — it only narrows it. Devices paired before
roles existed read as `owner`. Only an owner can mint an owner code, approve a request as
owner, or change a device's role; a device's own role is reported to it in
`server_info.callerRole`, and the daemon advertises the `deviceRoles` feature.

Roles are enforced on the HTTP API as well as the session RPCs: every
authenticated route declares a minimum role, routes that mint credentials (such as
the pairing offer) are owner-only, and a route that does not declare one requires at
least an operator. A credential below the route's role is refused with `403`.

The role comes from the credential wherever one is presented, on a direct connection and
over the relay alike: a viewer phone stays a viewer whichever way it reaches the daemon.
The daemon password and bearer-free trusted clients (loopback, trusted LAN) act as the
owner, because they carry no device identity. The Agent MCP endpoint requires an
`operator` or `owner` credential — a viewer credential is rejected there with `403`.

### Managing devices

Devices are managed from the app, in host settings **Devices**: the list of paired devices,
the queue of devices waiting for an owner's approval, renaming, role changes, revocation,
and minting a pairing code. See
[manage devices in the app](/docs/getting-started/connect-and-pair/#manage-devices-in-the-app).
The daemon advertises this as the `deviceAccess` feature (with `deviceRoles` and
`deviceRoleManagement`), and a client that does not see it says so instead of offering
buttons.

Changing a role takes effect on that device's live connections immediately. Revoking a
credential closes that device's live connections immediately; revoking the device you are
using is allowed, and ends that session.

Limits:

- There is no per-device revoke or role change from the CLI. `frogg auth reset-claim`
  removes all devices at once.
- The daemon has **no last-owner guard**: the last owner can be demoted or revoked, and a
  daemon with no owner can only be recovered from a shell on its own machine (loopback is
  trusted, so `frogg auth reset-claim` still works there). The app warns before such a
  change, but that warning is the client being careful — it is not enforced.

### Pairing links are confirmed, not automatic

A pairing link an app receives from outside — a deep link, a QR code, a `#pair/direct?…`
fragment on the web — is shown as a confirmation before anything is redeemed, so a link in
a message or on a web page cannot pair a device, or claim ownership of an unclaimed
daemon, on its own. The app proves the daemon's identity first and offers no button at all
when the key does not match the link, when the daemon cannot prove it holds its key, or
when a server it already knows presents a different key. See
[pairing links ask before they pair](/docs/getting-started/connect-and-pair/#pairing-links-ask-before-they-pair).

### Session presence

The daemon reports who else is on an agent or a terminal — device name and activity — to
everyone else on the same session, gated on the `sessionPresence` feature. It is
information, not a lock: two devices can write to the same agent at once, and the app
outlines the composer as a warning. Device names come from the other device, so treat them
as untrusted text. See
[shared sessions](/docs/using-frogg/shared-sessions/).

## Passwords

`frogg auth set-password` stores a scrypt hash (N=2^15, r=8, p=1) in `daemon.auth.password`;
bcrypt hashes written by older daemons are still accepted on login. `FROGG_PASSWORD` in the
daemon's environment overrides the stored hash, and while it does, the app reports the
setting as environment-controlled rather than letting you edit it. A password applies to
every client, including loopback, the web app and the MCP endpoint.

## Host and origin checks

- **Host header**: requests must use `localhost`, an IP address, the pairing host, or a
  hostname in `daemon.hostnames` / `FROGG_HOSTNAMES`. Others get `403 Invalid Host header`.
  This blocks DNS-rebinding attacks from web pages. The pairing host is allowed so you can
  reverse-proxy that name at the daemon; if you do not, set
  `daemon.allowPairingHostname: false` and the daemon stops answering to it.
- **CORS**: browsers may call the daemon only from its own origin, the desktop app, and
  `daemon.cors.allowedOrigins` / `FROGG_CORS_ORIGINS`. Avoid `*` outside development.
- **Proxies**: `X-Forwarded-For` is honoured only from `daemon.trustedProxies` (loopback by
  default), and the daemon walks the header from the right the way `proxy-addr` does. A
  forwarded client is never treated as loopback: the header is the caller's to write, so
  `X-Forwarded-For: 127.0.0.1` would otherwise hand any caller the most trusted locality
  there is. A proxy can still place a client on the LAN, which is trust `trustLan` opted
  into.

## Workspace services

A workspace service (a `frogg.json` script declared as a service) is a dev server the daemon
starts for you. It has no authentication of its own, so it binds to `127.0.0.1` by default
even when the daemon itself listens on `0.0.0.0`.

To reach one from another device, use the service URL the daemon hands out
(`<script>-<project>.localhost` or your `daemon.serviceProxy.publicBaseUrl`) and let the
daemon's service proxy carry the request. The proxy serves loopback clients directly; any
other client needs a paired device credential or the daemon password, exactly like the rest
of the API. Being on a trusted LAN is deliberately not enough here, because `trustLan`
defaults on.

`daemon.workspaceServices.bindHost: "0.0.0.0"` puts dev servers back on every interface.
That is an explicit choice to expose unauthenticated ports to the network; prefer the proxy.

If you publish services through your own reverse proxy with
`daemon.serviceProxy.listen`, that separate listener is not gated by the daemon's
credentials — your proxy owns access control for it.

## TLS and reverse proxies

The daemon serves plain HTTP and WebSocket. For TLS, terminate it in a proxy:

```text title="Caddyfile"
frogg.example.com {
  reverse_proxy 127.0.0.1:9999
}
```

```json title="~/.frogg/config.json"
{
  "daemon": {
    "listen": "127.0.0.1:9999",
    "hostnames": ["frogg.example.com"],
    "trustedProxies": ["loopback"],
    "auth": { "trustLan": false }
  }
}
```

Keep the proxy in `trustedProxies`, and set a password or pair devices. If the proxy is not
trusted, every proxied request looks like loopback and passes without credentials. Clients connect with **Use SSL** on, port 443.

## Relay

A relay lets clients reach a daemon with no inbound connectivity. Traffic is end-to-end
encrypted (Curve25519 key exchange, XSalsa20-Poly1305) with the daemon's public key from
the pairing offer, so the relay cannot read it.

Frogg does not operate a public relay, and no brand ships a relay endpoint. `packages/relay`
is a Cloudflare Durable Object implementation you can deploy yourself. Then set the
endpoint in the app under host settings, **Pair devices**, or with `daemon.relay.endpoint`
or `FROGG_RELAY_ENDPOINT`, and enable relay. TLS to the relay is on by default. Operating a
relay is not otherwise documented here.

If relay is enabled without an endpoint, the daemon starts, logs a warning and reports
relay as unavailable in pairing offers.

## MCP endpoint

`/mcp/agents` lets agents control the daemon, so it always demands a credential, whatever
the caller's locality — there is no "no password set, therefore open" case. It accepts:

- the per-agent bearer the daemon injects into an agent it started (this is also how the
  endpoint knows *which* agent is calling; it is never read from the request URL),
- the per-run capability token,
- a paired device credential with role `operator` or `owner`,
- the daemon password.

Anything else is `401`, and a `viewer` credential is `403`. Disable the endpoint with
`daemon.mcp.enabled: false` if you do not use agent orchestration.
