A Frogg daemon can run commands on its host through agents and terminals. Treat access to
it like SSH access to that machine.

## Access policy

| Client connects from | No password | Password set |
| -------------------- | ----------- | ------------ |
| Loopback | Allowed | Password |
| Private network (RFC 1918, link-local, `fc00::/7`) | Allowed while `trustLan` is on (default) | Password |
| Anywhere else, including CGNAT `100.64.0.0/10` (Tailscale) | Paired-device credential | Password |

Unauthenticated routes: `/api/identity` (version and brand, used by LAN scans),
`/api/health`, and the pairing setup routes. The web app's static files load without
credentials; its API calls do not.

### Recommended settings

| Deployment | Settings |
| ---------- | -------- |
| Laptop, daemon on the same machine | Defaults, or `--listen 127.0.0.1:9999` if nothing else should connect |
| Home or office LAN you control | Defaults |
| Shared or untrusted LAN | `frogg auth trust-lan off` and pair devices, or set a password |
| Tailscale / VPN | Pair devices (CGNAT addresses are not "private"), or set a password |
| Docker | Set `FROGG_PASSWORD`; container networking hides real client addresses |
| Public internet | Do not expose the daemon directly. Use a VPN, SSH, or a TLS reverse proxy plus a password |

## Pairing

Paired devices hold a random credential; the daemon stores only its SHA-256 in
`~/.frogg/principals.json` (mode 0600). Pairing tokens are single-use and expire after 10
minutes. See [connect and pair](/docs/getting-started/connect-and-pair/).

### Device roles

Every paired device holds one of three roles, enforced by the daemon on each request and on
streamed input (terminal keystrokes, agent messages, dictation, file writes):

| Role | Can |
| ---- | --- |
| `owner` | Everything: daemon settings and updates, provider accounts, pairing codes, approving and revoking devices, setting roles, password and claim settings |
| `operator` | Drive work: agent chats, terminals, workspace scripts, file edits, git and forge actions. No daemon settings, no device management |
| `viewer` | Read-only: sessions, timelines, terminal output, file browsing and diffs. No input, no command execution, no writes |

A role never widens what a device was granted — it only narrows it. Devices paired before
roles existed read as `owner`. Only an owner can change a device's role, and a device's own
role is reported to it in `server_info.callerRole`.

The daemon password and bearer-free trusted clients (loopback, trusted LAN) act as the
owner. Agents reaching the daemon over the MCP endpoint act as an operator and can never
manage devices.

Limits:

- There is no per-device revoke from the CLI. `frogg auth reset-claim` removes all devices.

## Passwords

`frogg auth set-password` stores a bcrypt hash in `daemon.auth.password`. `FROGG_PASSWORD` in
the daemon's environment overrides it. A password applies to every client, including
loopback, the web app and the MCP endpoint.

## Host and origin checks

- **Host header**: requests must use `localhost`, an IP address, the pairing host, or a
  hostname in `daemon.hostnames` / `FROGG_HOSTNAMES`. Others get `403 Invalid Host header`.
  This blocks DNS-rebinding attacks from web pages.
- **CORS**: browsers may call the daemon only from its own origin, the desktop app, and
  `daemon.cors.allowedOrigins` / `FROGG_CORS_ORIGINS`. Avoid `*` outside development.
- **Proxies**: `X-Forwarded-For` is honoured only from `daemon.trustedProxies` (loopback by
  default).

## TLS and reverse proxies

The daemon serves plain HTTP and WebSocket. For TLS, terminate it in a proxy:

```text title="Caddyfile"
frogg.example.com {
  reverse_proxy 127.0.0.1:9999
}
```

```json title="~/.frogg/config.json"
{
  "daemon": {
    "listen": "127.0.0.1:9999",
    "hostnames": ["frogg.example.com"],
    "trustedProxies": ["loopback"],
    "auth": { "trustLan": false }
  }
}
```

Keep the proxy in `trustedProxies`, and set a password or pair devices. If the proxy is not
trusted, every proxied request looks like loopback and passes without credentials. Clients connect with **Use SSL** on, port 443.

## Relay

A relay lets clients reach a daemon with no inbound connectivity. Traffic is end-to-end
encrypted (Curve25519 key exchange, XSalsa20-Poly1305) with the daemon's public key from
the pairing offer, so the relay cannot read it.

Frogg does not operate a public relay, and no brand ships a relay endpoint. `packages/relay`
is a Cloudflare Durable Object implementation you can deploy yourself. Then set the
endpoint in the app under host settings, **Pair devices**, or with `daemon.relay.endpoint`
or `FROGG_RELAY_ENDPOINT`, and enable relay. TLS to the relay is on by default. Operating a
relay is not otherwise documented here.

If relay is enabled without an endpoint, the daemon starts, logs a warning and reports
relay as unavailable in pairing offers.

## MCP endpoint

`/mcp/agents` lets agents control the daemon. Agents started by the daemon receive a
per-run token. With no password set, other clients that pass the access policy can use it
too. Disable it with `daemon.mcp.enabled: false` if you do not use agent orchestration.
