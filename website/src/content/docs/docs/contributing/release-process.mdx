This page describes how the official Frogg repository releases. If you maintain a fork, start with
[Build and release](/docs/fork-and-rebrand/build-and-release/) for brand variables and secrets.

## Versions

The root `package.json` `version` is the only version. Never edit a workspace version by hand.

```bash
npm run version:sync-internal
```

This runs `scripts/release/sync-workspace-versions.mjs`. It sets every workspace `version` to
the root version and rewrites internal `@frogg/*` dependency ranges: `*` for private workspaces,
the exact version for publishable ones. It also updates the version in the Rust manifest.

Give every release a `CHANGELOG.md` section headed `## <version>`, for example
`## 0.6.19 — 2026-09-13`. The workflow uses that section as the release notes. Without it, the
notes only say that no changelog entry exists.

## Cut a release

Betas ship from `main` and stable releases from `stable`. The day-to-day flow (betas,
backports, promotion) is in [Release streams](/docs/contributing/release-streams/); this is
what each command does. CI runs `release:beta` itself after every green push to `main` that
adds more than a release cut (the `beta` job in `ci.yml`), so you cut betas by hand only to
choose the line.

| Command                   | Branch   | Cuts                                                        |
| ------------------------- | -------- | ----------------------------------------------------------- |
| `npm run release:beta`    | `main`   | The next `X.Y.Z-beta.N`                                     |
| `npm run release:patch`   | `stable` | The next `X.Y.Z` (backported fixes)                         |
| `npm run release:promote` | `stable` | `X.Y.0` from `main`'s open beta line                        |

Each cut runs three steps:

- `release:check`: `npm install`, typechecks and clean builds of the library, server and CLI
  workspaces, then `npm pack --dry-run` for each publishable package. `release:beta` and
  `release:promote` accept `-- --skip-check`.
- `set-release-version.mjs`: runs `npm version <next> --include-workspace-root` with the
  message `chore(release): cut <version>`. npm's `version` hook syncs workspace versions,
  reinstalls, refreshes the Nix dependency hash (`nix:hash`, since the reinstall rewrites
  `package-lock.json`), and stages the result. This step needs either Nix or Docker on the
  machine cutting the release; without one the cut stops before it commits.
- `release:push`: creates the annotated tag `v<version>` if it is missing, pushes `HEAD` to
  the current branch (or `--branch <name>`), then pushes the tag.

Watch the **Release** workflow the tag starts. It publishes only when every required job
passes.

`release:push` refuses to continue when the local tag is not on `HEAD`, or when the remote tag
points at a different commit. It never moves an existing tag.

## Version modes

`scripts/release/set-release-version.mjs` computes the next version, or takes one with
`--version`. Preview it without changing anything:

```bash
node scripts/release/set-release-version.mjs --mode patch --print
npm run release:beta -- --print
```

Outside `--print` it enforces the streams in `frogg.json`: a beta version must be cut on the
development branch and a stable one on the stable branch; a stable `minor` or `major` is
refused (it arrives by promotion); a stable `patch` must stay below the open beta line on
`origin/main`. `FROGG_RELEASE_SKIP_STREAM_CHECK=1` turns the check off for a one-off repair.

| Mode         | npm script                      | From `0.6.19`   | From `0.6.20-beta.1` |
| ------------ | ------------------------------- | --------------- | -------------------- |
| `patch`      | `version:all:patch`             | `0.6.20`        | error                |
| `minor`      | `version:all:minor`             | `0.7.0`         | error                |
| `major`      | `version:all:major`             | `1.0.0`         | error                |
| `beta-patch` | `version:all:beta:patch`        | `0.6.20-beta.1` | error                |
| `beta-minor` | `version:all:beta:minor`        | `0.7.0-beta.1`  | error                |
| `beta-major` | `version:all:beta:major`        | `1.0.0-beta.1`  | error                |
| `beta-next`  | `version:all:beta:next`         | error           | `0.6.20-beta.2`      |
| `promote`    | `version:all:promote`           | error           | `0.6.20`             |

Only `-beta.N` prereleases are accepted. `release:beta` picks between `beta-minor` and
`beta-next` for you from the stable version, and in a fork from the upstream version it last
merged (`scripts/release/streams-core.mjs`).

## The release workflow

`.github/workflows/release.yml` runs on a pushed `v*` tag or by manual dispatch.

| Job                | What it does                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| `meta`             | Fails unless the tag matches `package.json` and is on its stream's branch (`streams.mjs assert-tag`: betas on `main`, stable on `stable`). Marks `-beta.N` versions as prerelease and picks the release's client: `classic` on stable, `frogg-next` on a prerelease (`none` when the brand's `next.enabled` is off). Detects optional secrets, picks the platform matrix, extracts release notes from `CHANGELOG.md`, creates a **draft** release titled after its client, uploads the install and uninstall scripts |
| `ui`               | Exports the web UI once (`npm run build:ui`)                                                     |
| `desktop`          | Stable only. Matrix: Windows x64, Linux x64 (`ubuntu-22.04`), macOS arm64 and x64. Runs `npm run build:desktop -- --target <target>` and uploads installers. Runs the Electron smoke test on the packaged Linux build |
| `daemon-build`     | Builds the server stack and bundles the shared web UI into the daemon                            |
| `daemon-bundle`    | Matrix: `linux-x64`, `linux-arm64`, `darwin-arm64`, `darwin-x64`, `win-x64`, `win-arm64`. Packs each bundle with a `.sha256` sidecar |
| `android`          | Stable only. Builds the arm64-v8a APK with `scripts/release/build-android-apk.mjs --serial`       |
| `next-desktop`     | Prereleases only. Calls `ui-next-desktop.yml`: Frogg Next for Windows x64, macOS arm64 and x64, and Linux (AppImage, deb), with its update feeds and one checksum list (Windows only with `platforms: default`). Runs a packaged launch smoke test on Linux. See [Frogg Next](#frogg-next) |
| `next-android`     | Prereleases only. Calls `ui-next-android.yml`: the Frogg Next arm64 APK                          |
| `updater-manifest` | Full builds only. Generates `release.json` with the release's `client`. On stable it also generates the classic Electron feeds and `SHA256SUMS-desktop` from the uploaded binaries; on a Frogg Next prerelease it names Frogg Next's feeds and checksum list. Then runs `verify-release-assets.mjs` |
| `docker`           | Only with Docker Hub credentials. Builds `deploy/docker/base/Dockerfile` for `linux/amd64` and pushes it |
| `publish`          | Clears the draft flag only if `meta`, `daemon-bundle` and `updater-manifest` succeeded, `docker` succeeded or was skipped, the run built all platforms, and the client's jobs succeeded: `desktop` and `android` on stable, `next-desktop` and `next-android` on a prerelease |

Every job builds the brand's one identity; the version alone decides what a release carries
(see [Release streams](/docs/contributing/release-streams/#what-a-release-carries)). A stable
tag carries the classic app and no Frogg Next files; a prerelease carries Frogg Next and none
of the classic app's payloads or feeds. Both carry the same daemon bundles and install scripts,
so a prerelease daemon installs into the normal home. `publish` marks a beta as a prerelease
and never Latest, and never moves Latest to an older version when two runs finish out of order.

Manual dispatch inputs:

- `tag` (required): an existing tag to build.
- `only`: `all` or `android`. `android` runs only `meta` and the client's APK job (`android` on
  stable, `next-android` on a prerelease).
- `platforms`: `default` builds the Windows x64 desktop client, `linux-x64` and `win-x64` daemon
  bundles, and the APK. `all` builds the full matrix. A tag push always builds everything.

A manual run with `platforms: default` or `only: android` skips `updater-manifest` and `publish`,
so its release stays a draft.

Uploads skip file names that already exist on the release. Only the workflow run that created
the release may overwrite (`--clobber`) its own assets.

### Build selected

`.github/workflows/build-selected.yml` builds workflow artifacts, not a release. Run it manually
with `target` set to `all`, `windows`, `daemon` or `android`, or call it from another workflow
(`workflow_call`). CI no longer calls it on pushes to `main`: a green push cuts a beta release
instead. It builds the classic app under the brand's one identity on every branch. It produces the Windows x64 client (after the desktop unit tests), the Linux x64 daemon
bundle, and a debug-signed arm64 APK. Artifacts are kept for 14 days.

## Release assets

Names come from `brand.artifactPrefix` (`Frogg`). Real examples from v0.6.19:

| Asset                                          | Source                                     |
| ---------------------------------------------- | ------------------------------------------ |
| `Frogg-0.6.19-win-x64.exe`, `.exe.blockmap`      | electron-builder NSIS                      |
| `Frogg-0.6.19-win-x64.zip`, `Frogg-0.6.19-win-x64-installer.zip` | portable ZIP, zipped installer |
| `Frogg-<v>-linux-x86_64.AppImage`, `Frogg-<v>-mac-{arm64,x64}.zip` | Update payloads the manifests require |
| `Frogg-0.6.19-linux-x86_64-daemon.tar.gz` + `.sha256` | daemon bundle (Windows bundles are `.zip`) |
| `frogg-daemon-0.6.19-linux-x64.tar.gz` + `.sha256` | legacy daemon name, still produced for the official brand |
| `Frogg-0.6.19-android-arm64-v8a-unsigned.apk`    | debug-signed APK                           |
| `release.json`                                 | product update descriptor                  |
| `electron-latest.yml`, `electron-latest-linux.yml`, `electron-latest-mac.yml` | classic Electron update feeds, stable releases only |
| `SHA256SUMS-desktop`                           | checksums of the classic desktop assets    |
| `install.sh`, `uninstall.sh`, `install-docker.sh`, `uninstall-docker.sh` | install scripts, every release |

The classic desktop, APK, feed and `SHA256SUMS-desktop` rows are on stable releases only. A
prerelease carries the daemon bundles, `release.json`, the install scripts and Frogg Next:

| Asset                                          | Source                                     |
| ---------------------------------------------- | ------------------------------------------ |
| `Frogg-Next-<v>-win-x64.{exe,zip}`, `-mac-{arm64,x64}.{dmg,zip}`, `-linux-x86_64.{AppImage,deb}` | Frogg Next desktop (`next-desktop`) |
| `<file>.blockmap` for the `.exe`, `.dmg` and Mac `.zip` files | differential updates (the AppImage embeds its own; the deb has none) |
| `frogg-next-latest.yml`, `frogg-next-latest-mac.yml`, `frogg-next-latest-linux.yml` | Frogg Next update feeds, uploaded after the files they name |
| `Frogg-Next-<v>-SHA256SUMS`                    | checksums of the Frogg Next assets         |
| `Frogg-Next-<v>-android-arm64-v8a.apk` (`-unsigned` without a keystore) | Frogg Next APK (`next-android`) |

Other desktop files (`.dmg`, `.deb`, Linux `.tar.gz`) follow the electron-builder pattern
`Frogg-<version>-<os>-<arch>.<ext>`. Check real names with
`gh release view <tag> --json assets` rather than guessing.

## Secrets

All secrets are optional. Without them the release still builds, with the limits noted.

| Purpose                     | Secrets                                                                                 | Without them |
| --------------------------- | --------------------------------------------------------------------------------------- | ------------ |
| Windows code signing (Azure Trusted Signing) | `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `TRUSTED_SIGNING_ENDPOINT`, `TRUSTED_SIGNING_ACCOUNT`, `TRUSTED_SIGNING_PROFILE` | Windows binaries (classic and Frogg Next) are unsigned |
| Android release keystore    | `FROGG_ANDROID_KEYSTORE_BASE64`, `FROGG_ANDROID_KEYSTORE_PASSWORD`, `FROGG_ANDROID_KEY_ALIAS` (default `frogg`), `FROGG_ANDROID_KEY_PASSWORD` | APK is debug-signed and named `-unsigned` |
| Frogg Next Android keystore override | `FROGG_NEXT_ANDROID_KEYSTORE_BASE64`, `FROGG_NEXT_ANDROID_KEYSTORE_PASSWORD`, `FROGG_NEXT_ANDROID_KEY_ALIAS`, `FROGG_NEXT_ANDROID_KEY_PASSWORD` | Frogg Next APK is signed with the classic `FROGG_ANDROID_*` key, or debug-signed and `-unsigned` without either |
| Docker Hub                  | `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`                                                  | `docker` job is skipped |
| External brand repository   | `BRANDING_READ_TOKEN`                                                                    | Only needed for a private brand repository |

macOS builds are not signed or notarized (`CSC_IDENTITY_AUTO_DISCOVERY=false`, `notarize: false`).

### Android signing

The published APK is currently debug-signed with the public Expo/React Native debug key and
named `-unsigned`. Android identifies an app by its signing key. Every APK published so far is
debug-signed, so switching to a release key would stop existing installs from updating in place;
users would have to uninstall and lose app data. Until that migration is planned, the workflow
warns and keeps shipping debug-signed APKs. Do not treat them as a distributable,
trusted build.

The in-app Android updater reads the installed app's own signing certificate and only offers an
asset with the same signing flavour, so a debug-signed install is offered the `-unsigned` APK
and a release-signed one is offered the plain APK. When both exist on a release, each install
follows its own path; when only the mismatched one exists, the app says so rather than starting
an install Android would reject. Keep publishing the flavour that matches what is installed.

### Frogg Next

Frogg Next (`apps/ui-next`) is the client prereleases ship. It installs under the brand's
[`next`](/docs/fork-and-rebrand/brand-manifest/#next) identity (for frogg: `Frogg Next`,
`app.frogg.next`, `frogg-next://`, `Frogg-Next-<version>-` assets), which the apps read from
`.generated/branding/brand.json`, so it installs beside the classic app:

- `.github/workflows/ui-next-desktop.yml` and `ui-next-android.yml` keep building workflow
  artifacts on pushes to `main`. `release.yml` calls them (`workflow_call`) with the tag and the
  `clobber` flag on prerelease tags, and `publish` requires them. Each uploads to the release,
  skipping names already there like every other upload.
- Frogg Next updates itself from its own electron-updater feeds,
  `<next.feedPrefix>-latest.yml`, `-latest-mac.yml` and `-latest-linux.yml`
  (`frogg-next-latest*.yml`). They never share a name with the classic `electron-latest*.yml`,
  so neither app can pick up the other's update.
- `release.json` on a prerelease records `client: "frogg-next"` and names those feeds and the
  checksum list. Its classic `electron-updater` path is a manual one whose message points an
  older classic beta install at Frogg Next. `verify-release-assets.mjs` checks the feeds and
  checksum list are uploaded, every payload they name is on the release, every checksum matches
  GitHub's digest, and no classic payload or `electron-*` feed is attached. On a stable release
  it checks no Frogg Next file is attached. `build-release-metadata.test.mjs` holds this.
- Windows builds are signed with the same Azure Trusted Signing secrets as the classic app.
  macOS builds are ad-hoc signed (no Apple Developer ID) and not notarized; the x64 build is
  cross-built on the arm64 runner. The APK is signed with the classic `FROGG_ANDROID_*` key (so a
  later promotion to the stable application id can update the classic app in place), unless the
  `FROGG_NEXT_ANDROID_*` override is set; without either it is debug-signed and `-unsigned`.
  Builds from `main` pushes are always debug-signed.
- The brand's `next.enabled` turns Frogg Next on or off. It defaults to on for upstream frogg
  and off for any other brand; with it off, prereleases carry only the daemon (see
  [Build and release](/docs/fork-and-rebrand/build-and-release/#frogg-next)).

An installed Frogg Next finds the newest prerelease that carries its platform's feed and points
electron-updater at that release. The Windows installer and the AppImage update in the
background and prompt for a restart; on macOS and with the deb the app offers the download
instead. The Android app updates itself from the prerelease's APK the same way.

Promotion later builds Frogg Next under the brand's stable identity as plain frogg and ships it
on stable releases in place of the classic app.

Check asset names without building:

```bash
node apps/ui-next/scripts/build-desktop.mjs --dry-run [--target darwin-arm64|darwin-x64|win32-x64|linux-x64]
node apps/ui-next/scripts/build-apk.mjs release-assets --dry-run
```

### Docker tags

The image name comes from `distribution.dockerImage` in the brand (`froggapp/frogg`). The job
pushes the exact version on every release, plus `<major>.<minor>`, `<major>` and `latest` for
stable versions. A prerelease image is only reachable by its exact tag
(`FROGG_VERSION=1.6.14-beta.2 bash install-docker.sh`).
If the exact version tag already exists, nothing is pushed. Fix a bad image by releasing a new
patch version.

`froggapp/frogg` on Docker Hub has no published tags. Until the job pushes one, user-facing
docs tell people to build the image locally (see [Docker](/docs/self-hosting/docker/)).

## Release rules

These come from `.claude/skills/frogg-release/SKILL.md`. Follow them for every release, local or CI.

- **Preserve the update path.** Installed clients discover updates through `release.json` and
  the Electron channel manifests. Keep the discovery name stable and keep compatibility
  manifests that shipped clients still read. Every existing update protocol needs a working
  automatic path or explicit manual migration instructions.
- **Never overwrite a versioned binary** with a different build. If only metadata is missing,
  regenerate it from the unchanged binaries:

  ```bash
  node scripts/release/build-release-metadata.mjs --version VERSION --client classic|frogg-next \
    --brand .generated/branding/brand.json --assets ASSETS --out METADATA
  node scripts/release/verify-release-assets.mjs --repo OWNER/REPO --tag vVERSION \
    --brand .generated/branding/brand.json
  ```

- **Build from one identified revision** and lockfile. Do not run two builds in the same
  worktree; they share output directories.
- **Keep the desktop app-only.** Daemon bundles are separate distributions. Do not bundle a
  daemon to make a desktop test pass.
- **Do not publish an incomplete release** by clearing the draft flag by hand. Fix the failed job
  first. Stop retrying when the same deterministic failure repeats.
- **Do not mark a beta as Latest.**
- **Keep each client on its own releases.** Stable releases carry the classic app; prereleases
  carry Frogg Next. Never attach classic payloads or `electron-*` feeds to a prerelease.
- **Keep tags** when you delete superseded drafts.
- **Report what was validated.** A successful upload is not a tested update. Separate packaging
  success, emulator launches and real installed-update checks, and list untested platforms in the
  release notes.

### Partial releases

When only some platforms are rebuilt, `build-release-metadata.mjs` accepts
`--retain-desktop-from <previous release.json>`. It keeps the Linux and macOS feed entries at
their earlier version, and the verifier requires those files and hashes to match the earlier
release. v0.6.19 shipped this way with the v0.6.13 Linux and macOS payloads. This path is manual:
build with `build-selected.yml`, upload, generate and verify metadata, then publish.
