Every change passes through three stages: **Development**, then **Beta**, then **Stable**.
Development runs on your machine with no CI. Beta is built by CI and reaches testers through
auto-update. Stable reaches users only when a maintainer promotes the beta line or backports a
fix.

## Three stages

| Stage       | Where it runs                        | Built by                  | Reaches                    | Updates           | Leaves when                            |
| ----------- | ------------------------------------ | ------------------------- | -------------------------- | ----------------- | -------------------------------------- |
| Development | a feature branch in its own worktree | you, locally (`dev:live`) | you, on the LAN            | edits reload live | it works and `verify --changed` passes |
| Beta        | `main`                               | CI, on every green push   | testers, as **frogg beta** | auto-update       | a maintainer promotes it               |
| Stable      | `stable`                             | CI, on promote or patch   | everyone, as **frogg**     | auto-update       | —                                      |

- **Development publishes nothing.** No tag, no update feed, no CI build. It runs from your
  checkout on its own ports and home (`.dev/live/home`), so it never touches an installed
  frogg or frogg beta. Point the installed app at it by adding its daemon as a host.
- **Beta is release validation.** Packaging, installers and the update path get tested here.
  It is not the first time a change runs; if it is, go back to Development.
- **Stable is never a default.** It moves only on an explicit instruction for that change.

## The flow

<Steps>

1. **Branch.** Work on a feature branch in its own worktree, so its dev daemon, ports and
   `.dev/` state stay apart from other work. Inside Frogg, the repository's `frogg.json` sets up
   each new worktree for you ([working on Frogg inside Frogg](/docs/contributing/development-setup/#working-on-frogg-inside-frogg)).

2. **Development: run it locally**, on the cheapest rung that exercises the change
   ([below](#test-locally-before-a-beta)). A beta is not the first time a change runs.

3. **Verify** what your diff can break, and update docs and UI strings in the same change:

   ```sh
   node scripts/ci/verify.mjs --changed
   ```

4. **Land on `main`.** Merge or push. CI runs format, lint, typecheck and the test suites.

5. **Beta: CI builds it.** When the `main` run is green, CI's `beta` job cuts the next `X.Y.Z-beta.N`
   (`node scripts/release/streams.mjs beta`), pushes the tag and starts the release build for
   every platform. Install the beta as **frogg beta**, beside your stable frogg, and test it
   there ([frogg beta installs beside frogg](/docs/contributing/release-streams/#frogg-beta-installs-beside-frogg)).
   A push that only cuts a release does not cut another beta.

6. **Stable: promote or backport.** Stable moves only on an explicit decision: `npm run release:promote` on
   `stable` ships the beta line, and `npm run release:backport` plus `npm run release:patch`
   ship a single fix early. Nothing merges from `stable` back into `main`.

</Steps>

:::caution[Stable is never a default]
Do not push, merge, cherry-pick or cut a release on `stable` without an explicit
instruction for that change. When in doubt, stop at `main`. This rule also binds AI agents
working in the repository (`AGENTS.md`).
:::

[Release streams](/docs/contributing/release-streams/) has every release command and option.

## Test locally before a beta

<Screenshot
  src={ladderDark}
  lightSrc={ladderLight}
  variant="bare"
  alt="Five rungs from cheapest to most complete. Rungs 1 to 4 are Development, local with no CI; rung 5 is Beta: npm run preview for UI, npm run dev:live for a feature end to end, dev:live added as a host in the installed app for daemon behaviour, npm run dev:desktop for the Electron shell, and a beta build for packaging, installers and auto-update."
/>

| Stage       | Rung                       | Command                                                  | Covers                                         |
| ----------- | -------------------------- | -------------------------------------------------------- | ---------------------------------------------- |
| Development | 1. Preview                 | `npm run preview`, then `npm run shot` / `npm run probe` | UI layout, copy, styling                       |
| Development | 2. Live                    | `npm run dev:live`, open the printed URL                 | A feature end to end with real providers       |
| Development | 3. Live, from the real app | `npm run dev:live`, add its daemon endpoint as a host    | Daemon behaviour behind an installed app build |
| Development | 4. Desktop                 | `npm run dev:desktop` on a machine with a display        | Electron shell, native bridge                  |
| Beta        | 5. Beta build              | A green push to `main`                                   | Packaging, installers, auto-update             |

- **Preview** starts an isolated daemon with a mock provider and a seeded demo project, plus
  the web app with hot reload. Nothing it does reaches your real providers.
- **Live** runs this checkout's daemon against your real provider logins, with a persistent
  home in `.dev/live/home`. UI edits hot-reload; server edits restart the daemon.
- **From the real app**: in an installed Frogg, add the daemon endpoint `dev:live` prints as a
  host. The installed app's own UI is unchanged, so check UI changes in the web URL.
- **Desktop** needs a display; on a headless machine stop at rung 3.

Ports, state and options for each are in
[development setup](/docs/contributing/development-setup/#preview-ui-changes).

## The inner loop

The inner loop is the Development stage.

<Screenshot
  src={loopDark}
  lightSrc={loopLight}
  variant="bare"
  alt="The Development stage, local with no CI: Edit, Run (npm run preview or dev:live), Check (npm run shot or probe) loop back to Edit until the change works. Then Verify (verify.mjs --changed), Docs and strings, then the Beta stage (Land on main, Beta built by CI with auto-update), and Stable by explicit promotion. Each step is labelled with the contributor skill that guides it."
/>

Keep one stack running and edit against it:

```sh
npm run preview          # or: npm run dev:live
```

Then check each edit without leaving the terminal:

```sh
npm run shot -- settings/general            # screenshot a route to .dev/shots/
npm run shot -- chat --mobile               # phone viewport
npm run probe -- --help                     # scripted text probes: layout, visibility, animation
npm run shot -- host/providers --live       # the same against dev:live
```

- `preview` and `dev:live` write their URLs to `.dev/preview/state.json` and
  `.dev/live/state.json`; `shot` and `probe` read them, so they need no arguments.
- A protocol or client change needs `npm run build:client`. `dev:live` restarts its daemon
  when the rebuilt output changes; reload the page too.
- Once it works, leave the loop: `verify --changed`, docs, UI copy in every locale, then
  land on `main`.

The [contributor skills](/docs/contributing/development-skills/) encode each step for AI
agents, and humans can read them as checklists.

## Branded distributions

A fork runs the same flow on its own `main` and `stable`, with upstream as a third stream.
See [develop a branded distribution](/docs/fork-and-rebrand/branded-development/).
