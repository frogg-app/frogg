The **Developer** settings section shows this app and the daemon on each host you have added,
and launches development daemons from a source checkout of frogg.

Prereleases are not installed from here. They ship as **Frogg Next**, a separate app, and a
host's daemon takes prerelease versions when its update channel is set to **Beta** in the
host's **Daemon & updates** settings (see [updates](/docs/self-hosting/updates/)).

## Turn it on

Open **Settings → About** and switch on **Developer options** at the bottom of the page. A
**Developer** section appears in the settings sidebar, just above **About**. The switch is a
preference of this app install; it is off by default and does not sync to other devices.
Switch it off to hide the section again.

Prerelease builds always show the **Developer** section, so they have no switch.

## Stable

**App** shows this app's name and version. **Daemons** lists every host you have added with
the daemon version this app is connected to, or that it is offline.

## Development daemon

**Development daemon** runs `npm run dev:live` from a source checkout of frogg on a host, so a
branch can be tried with real providers before it ships. It lists every workspace on
the host that is such a checkout, with its branch. **Launch** starts that checkout's daemon and
web app on free ports; each checkout runs its own, so several can run at once. **Stop** ends
one, and **Open web UI** opens its web app once it answers.

The quicker way is the **Dev** menu in the top bar, which follows the session in view: when its
worktree is a source checkout it offers **Launch dev build**, and once that runs it shows the
daemon and web app status and rebuilds, restarts, opens and stops it. Dev builds running for
other sessions are listed below, and their sidebar rows carry a **Dev** badge.

A dev build names itself `<hostname>-DEV-<checkout folder>` and starts with a copy of the
host daemon's provider accounts, projects and conversations, so nothing needs signing in
again. Continue a conversation in one daemon at a time: both write to the same provider
session. The launcher's output goes to `.dev/live/launcher.log` in the checkout, and a launch
that fails straight away shows that log's error.

It needs the **owner** role, Linux or macOS, and dependencies installed in the checkout
(`npm ci`). The development daemon cannot launch another one. When the daemon that launched it
runs as a systemd service, restarting that daemon stops the development daemon too.

## Dev bar

With developer options on, a bar under the sidebar header shows the development daemon and its
web app when a connected host manages one (or is one). Each has a dot: green running, amber
out of date, blue rebuilding, grey stopped. Its menu says why it is out of date, how many
commits the checkout is behind `origin/main`, and why the last rebuild failed, if it did.

| Pill       | Actions                                                                                  |
| ---------- | ---------------------------------------------------------------------------------------- |
| Dev daemon | **Rebuild and restart** (`npm run build:client`, then restart), **Stop**, **Start in** a checkout |
| Dev web    | **Open**, **Restart with a clear cache**                                                 |

"Out of date" means protocol or client source changed since the last build, dependencies changed
(run `npm ci`, then stop and start it), or the web app's config changed since it started. The
bar reaches `dev:live` through `.dev/live/control.json`, which the launcher writes on start, so
it also manages a `dev:live` you started by hand. Start and stop come from the host's
daemon; the development daemon itself can only rebuild and restart.
