## Model

- A **project** is a directory you registered on a daemon, usually a git repository.
  IDs look like `prj_a00e87f3186c7681`.
- A **session** is one working directory inside a project: the original checkout, a git
  worktree, or a plain directory. Agents, terminals and scripts run in a session. IDs
  look like `wks_b5b04560aaa0b892`.
- Projects and sessions belong to one daemon and are stored in
  `~/.frogg/projects/`.

## Session context

Above an active agent composer, Frogg always shows the session directory and its checked-out
branch as separate pills. For a Frogg-managed worktree, the directory pill identifies the source
project checkout rather than Frogg's internal worktree path. The `+` / `−` count beside them is
the current uncommitted working-tree diff, including
untracked text files; it does not include committed changes merely because the branch differs
from its base. Branch divergence remains available in the Git views.

Removing a project from the sidebar and archiving an ordinary session happen immediately and
do not change files on disk. Archiving a Frogg-managed worktree is different: it can remove the
managed worktree directory, so Frogg keeps its confirmation before that destructive operation.

## Add a project

- App: **Add project** in the sidebar, then choose a folder on the daemon host.
  Folders whose names start with `.` are hidden from folder lists and suggestions, including when choosing where to create or clone a project. Turn on **Settings > General > Show hidden folders** to list them, or type a path such as `~/.config` to open one directly.
- CLI: `frogg project create /path/to/repo`.

Starting an agent, session, terminal or script in a directory does not register it as a
project. Add the directory first, then choose its project or session.

Import existing Claude Code or Codex sessions with **Import session** on the home screen.
To bring in a whole project with its conversations, from the daemon host or from your
computer, use **Add project → Import project and conversations**; see
[Import projects and conversations](/docs/using-frogg/import-projects-and-conversations/).

## Sessions and worktrees

When you start work you choose **isolation**:

| Isolation  | What you get |
| ---------- | ------------ |
| `local`    | The agent works directly in the checkout |
| `worktree` | Frogg creates a git worktree on a new or existing branch; your checkout stays untouched |

Worktree modes:

| Mode              | Creates |
| ----------------- | ------- |
| `branch-off`      | A new branch from a base ref (`--base`) |
| `checkout-branch` | A worktree for an existing branch |
| `checkout-pr`     | A worktree for a pull request or merge request (`--pr-number`, `--forge`) |

```sh
frogg workspace create --isolation worktree --mode branch-off --new-branch feature/export
frogg agent run --new-workspace worktree --new-branch fix/flaky-test "Fix the flaky upload test"
```

Worktrees live under `~/.frogg/worktrees/<project hash>/<slug>`. Change the root with
`worktrees.root` in [config](/docs/reference/configuration/#worktrees). If you do not
name a branch, Frogg can generate one from the first prompt. A worktree stays grouped with its
main checkout's project; opening or resuming it does not add its worktree directory as another
project.

### Unfinished new-session forms

If you leave the new-session screen before launching, the sidebar shows a
**New session (draft)** row, with the project name when one is selected. Selecting it
reopens the form with its project, prompt, attachments, provider and model selections,
isolation and starting ref.

- A launch in progress stays locked while you navigate elsewhere, so returning to the draft
  cannot submit it twice.
- If the launch fails, the draft stays in the sidebar with its error so you can retry.
- A successful launch removes the draft.
- The draft rows are kept in memory only. Reloading or restarting the app clears them.

Archiving a session removes its Frogg-owned worktree once nothing else uses it:

```sh
frogg workspace archive wks_b5b04560aaa0b892
```

## Prepare new worktrees

A fresh worktree has no `node_modules`, `.env` or build output. Describe setup in
`frogg.json` at the repository root:

```json title="frogg.json"
{
  "worktree": {
    "setup": ["npm ci", "cp \"$FROGG_SOURCE_CHECKOUT_PATH/.env\" .env"],
    "teardown": "docker compose down"
  }
}
```

The app nudges you with **Set up worktree scripts** until a project has setup commands.

## Scripts and services

`frogg.json` scripts run in a session. A **service** gets its own port, env vars and a
proxy URL, so the same dev server can run in several worktrees at once.

```json title="frogg.json"
{
  "scripts": {
    "api": { "type": "service", "command": "npm run dev -- --port $FROGG_PORT" },
    "test": { "command": "npm test" }
  }
}
```

```sh
frogg script start api
frogg script ls
```

Full reference: [project config](/docs/reference/project-config/).

## Terminals

Each session can have terminals in the app. The CLI and agents can drive them too:

```sh
frogg terminal create --name build
frogg terminal send-keys <terminal-id> "npm run build" Enter
frogg terminal capture <terminal-id> --scrollback
```

## Organize the sidebar

The display menu at the top of the sidebar controls how sessions are arranged.

- **Grouping** puts sessions under their project or under their status.
- **Sort** orders sessions within each group, and orders projects when grouped by project:
  - **Recent activity** (default): the most recently active session first. A project ranks by
    its most recently active session.
  - **Date created**: the newest session first. A project ranks by when it was added, or by its
    oldest session if the host does not report that. Creation times come from the daemon's
    session and project records; sessions carried over from before those records existed use
    the time of their earliest agent. The option is greyed out until every connected host runs a
    daemon that reports creation times. If it was chosen before, the sidebar sorts by recent
    activity while such a host is connected and keeps the choice for later.
  - **Name**: A to Z.
  - **Needs attention first**: needs input, failed, ready to review, working, then done. Within
    one status, the most recent change comes first.
  - **Manual**: the order you set by dragging.
- **Reverse order** flips the chosen sort. It is not available for Manual.
- Items that tie are ordered by name, so rows do not swap places as agents report activity.
- Dragging a project or session while a sort is active keeps the order on screen and switches
  the sort to **Manual**.
- Pinned sessions keep their own drag order.

Grouping and sort are saved on the device. The sidebar starts on **Recent activity**, including
after updating from a version without sorting; your saved drag order is kept for **Manual**.

## Labels and archiving

- Sessions can be renamed (`frogg workspace rename`) and labelled in the app.
- Archived agents and sessions disappear from the sidebar but keep their history.
  `frogg agent ls -a` includes archived agents.
- **History** in the menu lists every session across all connected hosts, archived ones
  included. A project's menu has **Show archived sessions**, which opens the same list
  scoped to that one project on its own host: the header names the project, the host
  filter is not shown because the view is already tied to one host, and search still
  works within the scope.

## Merge handover

When you use **Merge locally** from a worktree, Frogg resolves the target branch on the same host and project. After a successful merge it opens an existing target session when one is already present; otherwise the source session remains available and Frogg reports that the target could not be resolved. The conversation, timeline, drafts and attachments stay with the active session context.

The source worktree is archived only after a clean successful merge and target resolution. Archiving uses the recoverable session archive flow. If cleanup fails, the merge remains successful, the source session is retained, and the UI reports the partial result so you can retry archive manually. Dirty worktrees and merge conflicts never trigger handover or archiving.
