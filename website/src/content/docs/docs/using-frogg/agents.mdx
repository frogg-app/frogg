An agent is one conversation with a provider (Claude Code, Codex, OpenCode...) running
on the daemon in a session. The daemon keeps its state and timeline, so every client
sees the same agent and it keeps running when clients disconnect.

<Screenshot src={appAgentTimelineImg} alt="Agent timeline in a session" />

## States

| State          | Meaning |
| -------------- | ------- |
| `initializing` | The provider process is starting |
| `running`      | A turn is in progress |
| `idle`         | Waiting for your next message |
| `error`        | The provider failed; the timeline shows why |
| `closed`       | The runtime stopped. The agent can be resumed from its history |

## Start an agent

In a session, type in the composer and pick:

- **Model** and, where the provider offers one, a **thinking** level,
- **Account**, but only when the provider has more than the one sign-in — see
  [which account an agent uses](/docs/agents-and-providers/providers/#which-account-an-agent-uses),
- **Mode**, which decides what runs without asking (see [permissions](/docs/using-frogg/permissions/)).

Mention files with `@`, use `/` for provider commands and skills, and attach images or
files with **+** or drag and drop. Each file can be at most 50 MB; larger files are
rejected with an error before Frogg reads them.

Returning to a Claude conversation that has been sitting for more than an hour outlines the
composer in amber and notes, in its corner, how many input tokens the next message re-sends.
Past that hour the conversation's prompt cache has lapsed, so the next message pays full
input price for the whole context rather than continuing cheaply from the cache.

From the CLI:

```sh
frogg agent run --provider codex/gpt-5.5 --mode auto --cwd ~/code/api "Add rate limiting to /login"
```

## Steer or queue

While an agent is running, **Enter** steers the active turn with your new message and
**Cmd/Ctrl+Enter** queues it for after the turn. Swap these in **Settings → General →
Default send**.

If another device is on the same agent, the composer says so and outlines itself in amber.
It stays usable; see [shared sessions](/docs/using-frogg/shared-sessions/).

## The timeline

The timeline shows messages, tool calls (reads, edits, shell commands), diffs, permission
requests and results. Per message you can copy it, **rewind** to it, or **fork chat from
here** to start a new agent with the conversation up to that point.

Read it from a terminal:

```sh
frogg agent logs <id> --tail 50
frogg agent logs <id> --follow --filter tools
```

## Stop, archive, delete

| Action  | CLI                      | Effect |
| ------- | ------------------------ | ------ |
| Stop    | `frogg agent stop <id>`    | Interrupts the current turn (stop button in the composer) |
| Archive | `frogg agent archive <id>` | Closes the runtime and hides the agent; history is kept |
| Delete  | `frogg agent delete <id>`  | Removes the agent |
| Reload  | `frogg agent reload <id>`  | Restarts the provider process, for example to pick up new skills, MCP servers or a login |

Archiving a parent archives its subagents, except those open elsewhere or in another
session, which are detached instead.

## Subagents

Agents can create agents. With the Frogg MCP tools or the `frogg` CLI, an agent runs
`frogg agent run` (or `create_agent`) and the child is labelled with its parent. Children
created this way run in the background and notify the parent when they finish. Provider
native subagents (for example Claude Code tasks) also appear under their parent.

### Claude Code workflows

When a Claude Code agent runs the Workflow tool, the run appears as a **Workflow** row in
the subagents track, and each agent the workflow fans out is listed beneath it, indented
one level. A child row shows the label the workflow gave it, its phase, model and token
use, and its status as it changes from running to finished. Selecting one opens its own
timeline, the same as any other subagent.

Children appear while the run is still in progress and keep updating until it finishes.
Frogg reads them from the run's own directory, so reopening the session later rebuilds
the same rows from history.

Make a subagent independent without stopping it. Detaching is not confirmed: nothing is lost,
the agent keeps its history, and the app opens it and confirms with a toast.

```sh
frogg agent detach <child-id>
```

## After a daemon restart

Agents that were in the middle of a turn when the daemon stopped are resumed with a
continuation prompt when it starts again, if the interruption was less than an hour ago.

To keep agent processes alive across daemon restarts entirely, opt in to independent
execution with `FROGG_EXECUTION_SERVICE=1` on the daemon. It is off by default; check it
with `frogg execution-status`.

## Scripted use

`frogg agent run` waits for the agent by default and exits when it is idle. Useful flags for
automation:

```sh
frogg agent run --wait-timeout 10m --output-schema ./result.schema.json --json \
  --provider claude "Summarize open TODOs as JSON"
frogg agent run -d --label ticket=ENG-142 "Investigate ENG-142"
frogg agent ls --label ticket=ENG-142
frogg agent wait <id> --timeout 600
```
