## Who can connect

The daemon decides per request, based on where the client connects from.

| Client address                                  | No password set                                   | Password set |
| ----------------------------------------------- | ------------------------------------------------- | ------------ |
| Loopback (`127.0.0.1`, `::1`)                   | Allowed                                           | Password required |
| Private network (10/8, 172.16/12, 192.168/16, link-local, fc00::/7) | Allowed while **LAN trust** is on (default) | Password required |
| Anything else (public IPs, CGNAT `100.64/10` such as Tailscale) | A **paired device** credential is required | Password required |

So on a home or office LAN, a fresh daemon is usable immediately. From anywhere else,
a device must pair first.

:::caution
LAN trust means anyone on your private network can control agents on the daemon. Turn
it off on shared networks: `frogg auth trust-lan off`, or set a password.
:::

**Claim mode** goes further: with `daemon.auth.claimMode: true` (or `FROGG_CLAIM_MODE=1`)
the LAN is never trusted, every client needs a credential, and the first client to reach
an unclaimed daemon claims it as owner. Frogg ships with it off; brands built from this
repo default it on. See [security and access](/docs/self-hosting/security/#claim-mode).

## Add a host in the app

Open **Hosts** in the sidebar.

<Screenshot src={appHostsImg} alt="Hosts menu with Direct connection and Paste pairing link" />

| Method              | Where           | Use when |
| ------------------- | --------------- | -------- |
| **Direct connection** | All clients   | The daemon is reachable by IP or name: LAN, VPN, Tailscale |
| **Remote SSH**      | Desktop app     | You can SSH to the host. The app tunnels to the daemon over SSH and can install it for you |
| **Paste pairing link** | All clients  | You have a link from `frogg auth pair` |
| **Enter a pairing code** | All clients | You have an `XXXX-XXXX` code from `frogg pair` |
| **Scan QR code**    | Android app     | The QR code printed by `frogg pair` or `frogg auth pair` |

### Direct connection

<Screenshot src={appDirectConnectionImg} alt="Direct connection dialog" />

Enter the host and port (9999 by default). The dialog also scans your local network for
daemons. **Use SSL** only if a TLS-terminating proxy sits in front of the daemon; the
daemon itself speaks plain HTTP and WebSocket. Enter the daemon password if you set one.

### Remote SSH (desktop)

The desktop app runs your system `ssh` with your SSH config (keys, users, ports, jump
hosts) and forwards a connection to the daemon's port on the remote host. Nothing is
exposed on the network. If no daemon is installed there, the app offers to **deploy**
one with the same install script; see [desktop app](/docs/desktop-mobile-cli/desktop/#remote-ssh).

## Pair a device with a code

`frogg pair` is the short way: it mints an 8-symbol code, valid for 10 minutes by default,
that one device can redeem once.

```sh
frogg pair
```

```text
Pairing code: ABCD-2345
Daemon address: 192.168.1.10:9999
Daemon fingerprint: sha256:8Qp1…
Role: operator
Expires: 2026-09-22T10:00:00.000Z

frogg://pair/direct?v=1&host=192.168.1.10&port=9999&fp=sha256%3A8Qp1…&pairingCode=ABCD-2345
```

A QR of that deep link follows on a real terminal, so an Android phone can scan it. Open
the deep link, scan the QR, or type the code into the app.

The device checks the `fingerprint` before it sends anything: it asks the daemon to sign a
nonce it chose and verifies the signature against that fingerprint. Pairing is two-way, so
a daemon impersonating yours cannot collect the code.

Useful flags: `--role viewer` for a read-only device, `--ttl 60` for a code that dies
quickly, `--json` or `--code-only` for scripts. See
[the CLI reference](/docs/desktop-mobile-cli/cli/#frogg-pair).

An owner can mint the same code from the app instead, in host settings **Devices** — see
[manage devices](#manage-devices-in-the-app).

### Type the code into the app

**Hosts → Enter a pairing code** takes the host address and the 8-character code.

<Screenshot src={appPairWithCodeImg} alt="Enter a pairing code dialog with a host address and code field" />

<Steps>

1. Enter `host:port` (and tick **Connect with TLS** only if a TLS proxy fronts the daemon),
   then the code. It is upper-cased and grouped as you type, and `I` and `L` are read as
   `1` and `O` as `0`, so a misread character still works.

2. Press **Check this host**. The app asks the daemon to prove it holds its own key and
   shows the resulting fingerprint. Nothing is redeemed yet.

3. Compare that fingerprint with the one on the owner's screen — `frogg pair` prints it,
   and so does the pairing code card in host settings **Devices**. Press **Pair** only if
   they match.

</Steps>

The check can refuse before you get that far: the host did not answer, it could not prove
it holds its key, or the server is already known here under a different key.

## Pair a device with a link

Pairing gives a device a long-lived credential. It is how you connect from outside the
private network, and it is required when LAN trust is off or claim mode is on.

<Steps>

1. On the daemon host, print a pairing link:

   ```sh
   frogg auth pair
   ```

   ```text
   Pairing link (phone, QR, or paste into the app):
   https://pair.frogg.app/code/eyJ2IjozLCJwcm9kdWN0IjoiZnJvZ2ci...

   Treat this pairing link like a password. Anyone with it can access this daemon.
   Access: LAN trusted — devices on your private network connect without pairing; anyone else must pair.
   Direct LAN pairing: this daemon has not been claimed yet; the first device to pair becomes its owner. Single-use, expires ...
   ```

   A QR code follows unless `FROGG_PAIRING_QR=0`.

2. Open the link on the device, scan the QR code in the Android app, or use **Paste
   pairing link** in any client.

3. The client connects to an address in the offer and redeems its one-time token. The
   daemon stores the device's credential as a hash in `~/.frogg/principals.json`.

</Steps>

Details that matter:

- Claim tokens are **single-use** and expire after **10 minutes**. Run `frogg auth pair`
  again for another device.
- The **first device to pair claims** an unclaimed daemon. Until then, a browser opening
  the daemon from a public address sees a pairing page instead of the app.
- Once claimed, a daemon stays claimed even if every device is removed; only
  `frogg auth reset-claim` reopens it. The last owner device cannot be removed or demoted.
- The link contains everything needed to connect. `pair.frogg.app` is a stateless page
  that hands the offer to the app; it never contacts your daemon. Change its base with
  `app.pairingBaseUrl` or `FROGG_PAIRING_BASE_URL`.
- A direct pairing offer lists the daemon's LAN addresses. The device must be able to
  reach one of them (same network or a VPN). Override the advertised address with
  `FROGG_PRIMARY_LAN_IP`.

In the app, host settings **Pair a device** first asks whether to enable relay. Frogg does
not run a public relay; choose **Not now** unless you
[operate one](/docs/self-hosting/security/#relay). If the host has no relay endpoint, the
dialog says so and offers only **Not now**. Set the endpoint, and whether to use TLS, in
the **Relay endpoint** card on the same **Pair devices** page, then pair again.

<Screenshot src={appPairDeviceImg} alt="Pair a device dialog asking whether to enable relay" />

### Device roles

Each paired device is an owner, an operator or a viewer, and the daemon enforces that role
on every request. New devices pair as owners unless the owner picks another role; only an
owner can change a device's role afterwards. See
[device roles](/docs/self-hosting/security/#device-roles) for what each role may do.

## Manage devices in the app

Host settings **Devices** is where a paired device is approved, renamed, re-roled or
revoked. Open **Settings → the host → Devices**.

<Screenshot src={appHostDevicesImg} alt="Host settings, Devices, showing Your access, Waiting for approval, Paired devices and Pairing code" />

| Card | What it does |
| ---- | ------------ |
| **Your access** | This device's own role and what it may do. A connection with no device credential — loopback, or a trusted LAN — is shown as an owner, because that is how the daemon treats it |
| **Waiting for approval** | Devices that asked to join. Approve one with the role it should get, or deny it. The name comes from the requesting device, so it is shown as plain untrusted text and the card says so |
| **Paired devices** | Name, role, when each was last seen, and which one is you. An owner can rename, change role and revoke |
| **Pairing code** | Mint a code for a new device with the role it should get, with a countdown, a QR of the pairing link, and the daemon's key fingerprint to read out |

Only an owner gets the buttons. An operator or a viewer sees the same list read-only, with
a line saying which role the action needs rather than a button that would be refused.

Revoking a device closes its live connections at once; revoking the device you are using
ends the session, and is confirmed separately. A revoked device's app drops its saved
credential and asks to pair again. The daemon refuses to revoke or demote the last owner;
promote another device first.

## Check and reset

```sh
frogg auth claim-status
```

```text
Claimed:        yes (2026-09-24T01:53:22.172Z)
Password:       not configured
LAN trusted:    yes (frogg daemon trust-lan off to require pairing on the LAN)
Principals:     /home/you/.frogg/principals.json
Daemon:         reachable at 0.0.0.0:9999 (pairingRequired=false, connectedClients=1)
```

`Claimed` is true when device credentials are saved, when the claim latch is set (it stays
set after every device is revoked) or when `config.json` sets a password. It does not show
whether anyone is using the daemon now. For automation, use `frogg auth claim-status --json` and read
`daemon.connectedClients` for live authenticated WebSocket sessions and
`daemon.pairingRequired` for the daemon's current access decision. The top-level claim fields
describe persisted configuration only.

The CLI has no per-device revoke or role change; do that in the app under
[Devices](#manage-devices-in-the-app). To start over from a shell, forget **all** devices
and pair the ones you keep again:

```sh
frogg auth reset-claim
```

## Pairing links ask before they pair

Opening a pairing link — from a message, a web page, a QR code or a terminal — never pairs
on its own. The app shows a confirmation first, and only a button press mints a credential.

<Screenshot src={appPairConfirmClaimImg} alt="Pairing confirmation showing the address, name, key fingerprint and a claim warning" />

The confirmation states the address, the host's name, its key fingerprint, the link's
expiry, and the role the link grants. A link that would **claim** the daemon — take
ownership of the machine and its agents — says so in a warning above everything else, and
its button reads **Claim this host**.

While it is on screen the app verifies the daemon's identity, which is read-only: it asks
the daemon at that address to sign a challenge and checks the signature against the
fingerprint in the link. There is **no Pair button at all** when:

- the daemon's key does not match the fingerprint in the link,
- the daemon cannot prove it holds its own key, or
- that server ID is already known on this device under a different key. The app pins a
  daemon's fingerprint after a successful pair, so a second link pointing a familiar server
  at a new key is refused rather than retried.

A daemon that simply did not answer is a retry, not a refusal.

### Direct pairing links

`frogg pair` prints a link of this shape, and the app handles it on every platform:

```text
frogg://pair/direct?v=1&host=192.168.1.10&port=9999&fp=sha256%3A8Qp1…&pairingCode=ABCD-2345
```

| Parameter | Meaning |
| --------- | ------- |
| `v` | Link version, `1` |
| `host`, `port` | Where the daemon is |
| `fp` | The daemon's key fingerprint, URL-encoded |
| `pairingCode` | The code to redeem, when the link carries one |
| `claim=1` | Claim the daemon as owner instead of redeeming a code |
| `tls=1` | Reach the daemon over TLS |
| `sid` | The daemon's server ID |
| `name` | A display name for the host |
| `role` | The role the link grants |

A browser cannot navigate to a custom scheme, so the web app accepts the same parameters as
a fragment on an ordinary page: `https://…/#pair/direct?v=1&host=…`.

## Use a password instead

A password applies to every client, including loopback and the LAN:

```sh
frogg auth set-password     # prompts, stores a scrypt hash in config.json
frogg restart
```

Clients enter it in **Direct connection**; the CLI reads `FROGG_PASSWORD` (`<PREFIX>_PASSWORD`
on a branded build). Docker and other automated installs can pass `FROGG_PASSWORD` as an
environment variable instead; never put it on a command line. A daemon with a password
counts as claimed. See [provisioning](/docs/self-hosting/provisioning/) for scripted installs.

## Troubleshooting connections

| Symptom | Fix |
| ------- | --- |
| `This app requires daemon 0.6.0 or later` | Update the daemon (`frogg update` or re-run `install.sh`), then restart its service |
| `Invalid Host header` (HTTP 403) | You reached the daemon by a hostname it does not allow. Add it: `frogg start --hostnames build-box.lan` or `daemon.hostnames` in config |
| `requires a password` from the CLI | Set `FROGG_PASSWORD` |
| `The daemon refused to create a pairing offer (HTTP 401)` from `frogg auth pair` | The CLI could not read the daemon home's `local-token`. Run it as the user that owns the daemon home, or set `FROGG_PASSWORD` |
| `This daemon can only be claimed from the host itself` (HTTP 403) | The daemon has `claimScope: "local"`. Run `frogg auth claim` on the host, or mint a code there with `frogg pair` and redeem that |
| Browser shows a pairing page | You are connecting from a non-private address. Pair, or connect over the LAN/VPN |
| Host says it **no longer accepts this device's saved credential** | The daemon refused the stored credential (device revoked, password changed, or daemon reset). The app deletes it and stops retrying; choose **Pair again** on the host's settings page. A `Too many failed attempts` refusal is temporary and keeps retrying |
| TLS error on Direct connection | Untick **Use SSL** unless a TLS proxy fronts the daemon |

More in [troubleshooting](/docs/self-hosting/troubleshooting/).
